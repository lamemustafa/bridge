## Tools to add to `bridge-mcp`

1. `voucher_schema` — returns the JSON schema an agent must produce: `{company_guid, vouchers:[{bridge_txn_id (client-supplied, unique, ≤64 chars, [A-Za-z0-9-_]), date YYYY-MM-DD, voucher_type ("Payment"|"Receipt"|"Journal"|"Contra"), narration?, reference?, entries:[{ledger, amount (decimal string, 2dp), side ("Dr"|"Cr")}]}]}` plus the rules (balanced Dr=Cr per voucher, ≥2 entries, date within the company's books-from..today, ledger names exact).
2. `validate_masters` — args `company_guid`, `ledgers:[string]`. Reads the live ledger catalogue (reuse Goal 1's ledger read) and returns per name: `exact` | `near_miss` (candidates found by NFC normalisation, case-fold, trimmed/collapsed whitespace, Unicode-confusable dash/quote folding, prefix match — return the exact live spelling to use) | `missing`. Never auto-create masters. Include the catalogue evidence hash.
3. `build_import_xml` — args: the voucher payload above. Steps: validate schema and arithmetic with `ExactDecimal`; run `validate_masters` internally and refuse the whole batch if any ledger is not `exact` (return the near-miss report); check dates against the company extent; check `bridge_txn_id` uniqueness within the batch and against `<data_dir>/agent-import-ledger.jsonl` (append-only record of every built batch: batch_id, txn ids, date range, sha256, built_at, status); render a Tally import XML file: `<ENVELOPE><HEADER><TALLYREQUEST>Import Data</TALLYREQUEST></HEADER><BODY><IMPORTDATA><REQUESTDESC><REPORTNAME>Vouchers</REPORTNAME><STATICVARIABLES><SVCURRENTCOMPANY>…</SVCURRENTCOMPANY></STATICVARIABLES></REQUESTDESC><REQUESTDATA>…<TALLYMESSAGE xmlns:UDF="TallyUDF"><VOUCHER REMOTEID="{bridge_txn_id}" VCHTYPE="{type}" ACTION="Create" OBJVIEW="Accounting Voucher View"><DATE>YYYYMMDD</DATE><VOUCHERTYPENAME>…</VOUCHERTYPENAME><NARRATION>…</NARRATION><ALLLEDGERENTRIES.LIST><LEDGERNAME>…</LEDGERNAME><ISDEEMEDPOSITIVE>Yes|No</ISDEEMEDPOSITIVE><AMOUNT>…</AMOUNT></ALLLEDGERENTRIES.LIST>…</VOUCHER></TALLYMESSAGE>…` — use Tally's sign convention (debit entries negative amount with ISDEEMEDPOSITIVE=Yes, credit positive with No; confirm against any sample in `.bridge-live` captures or the protocol reference and state your basis in the report), XML-escape everything, write UTF-8 with the `<?xml version="1.0" encoding="UTF-8"?>` declaration to `<data_dir>/imports/<batch_id>.xml`, and return `{batch_id, path, sha256, voucher_count, total_debit, total_credit, warnings, next_step: "Import this file in Tally (Gateway of Tally → Import → Vouchers) with the company open, then call verify_import"}`. Record a `PreImportMark` = current company ALTVCHID/ALTMSTID if Goal 1 exposes them, else the latest voucher ALTERID seen; store it in the ledger line.
4. `verify_import` — args `company_guid`, `batch_id`. Reads back vouchers in the batch's date window (literal `<FILTERS>` dates) fetching DATE, VOUCHERTYPENAME, REMOTEID, GUID, ALTERID, NARRATION, ALLLEDGERENTRIES.LEDGERNAME/.AMOUNT/.ISDEEMEDPOSITIVE. For each txn id: `posted_verified` (REMOTEID found, entries match ledger set + amounts exactly), `posted_divergent` (found but fields differ — list diffs), `not_found`. Also detect duplicates (same REMOTEID twice, or same date+type+ledger-set+amount fingerprint with different REMOTEID) and report them. Compute the AlterID delta versus the PreImportMark. Write `<data_dir>/imports/<batch_id>.proof.json` and `.proof.md` (a one-page Proof-of-Post: company identity, batch hash, counts, per-voucher status, evidence hashes, timestamp) and update the import ledger status. Never re-dispatch anything.

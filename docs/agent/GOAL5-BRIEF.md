## Findings

1. **`agent_import.rs:694` — XML-unescape text before comparing.** A ledger named `R&D` reads back as `R&amp;D`; `BytesText::decode()` does not unescape entities, so `verify_import` reports `posted_divergent` after a good import, and the voucher tools expose escaped names. Use the established tolerant protocol parsing/unescape path (see `bridge_tally_protocol::tolerant_xml`) for every text node before building records. Test: ledger and party names containing `&`, `<`, `"`, and a numeric entity, through both `vouchers` and `verify_import`.
2. **`agent_import.rs:790` — fingerprint fallback needs post-build evidence.** When the narration marker is absent, the fallback accepts any single voucher in the window with the same type and signed entries, including one that pre-dated the batch. Require that a fingerprint-only match be attributable: (a) the matched voucher's `ALTERID` must be greater than the batch's `pre_import_mark` (voucher axis) recorded at build time, or (b) the marker must be present; otherwise classify as `not_attributable` (never `posted_verified`). Persist the pre-import voucher/master marks with the batch and use them in verification. Test: a pre-existing identical voucher below the mark → `not_attributable`; a post-mark one → `posted_verified`.
3. **`agent.rs:611` — prove change-feed scans complete before advancing checkpoints.** A Tally-truncated collection still returns `STATUS=1` on its well-formed prefix. Do not derive completeness from the parsed prefix alone: corroborate the scan (e.g. the paired-read/bracket mechanism the runtime already uses, plus a count/high-water consistency check such as comparing the maximum observed `ALTERID` against the company high-water and requiring the response to be complete per the transport's completeness signal). Only publish `next_voucher_alter_id`/`next_master_alter_id` as advanceable when corroborated; otherwise return them with `checkpoint_advanceable: false` and a reason. Test: simulate a truncated response and assert the checkpoint is not advanceable.
4. **`agent.rs:554` — verify requested voucher windows before reporting completion.** Tally can silently widen or collapse a window whose boundary it rejects (documented Education-mode day-15/30 behaviour; `SVFROMDATE/SVTODATE` never scope collections). After parsing, assert every returned date lies within the requested window and, for an empty result, corroborate emptiness with a strictly wider window read (the H2 plan's "empty segment is never trusted on its own evidence" rule) before `evidence.state = "complete"`; otherwise `partial` with `window_not_honoured` or `empty_uncorroborated`. Test both.
5. **`agent.rs:1241` — numeric high-water checkpoints.** `next_*_alter_id` are emitted as JSON strings while the input schema requires integers and the handler uses `as_u64()` (defaulting to zero → full replay). Parse observed checkpoints into typed integers, fail closed when absent/malformed, and accept both integer and numeric-string input defensively. Test: round-trip `next_voucher_alter_id` into the next call.
6. **`agent.rs:75` — enforce `BRIDGE_AGENT_MAX_BYTES`.** The README advertises a 200,000-byte default but nothing applies it. Parse it in settings; after serialisation, if the response exceeds the cap, truncate rows (preferring to drop trailing rows and set `truncated: true` with `next_offset`) or refuse with a typed error when a single row exceeds the cap; record the enforced size in the egress receipt. Test with a low cap.
7. **`agent_import.rs:490` — accounting-day defaults in the Tally host's local calendar.** Replace `Utc::now()` date defaults (voucher date upper bound, `as_of` default) with the local date of the machine running Tally (Bridge runs on the same machine as Tally; use `chrono::Local`), and document it. Test: mock/inject a clock east of UTC around midnight.
8. **`agent.rs:523` — `rows_returned` must be the page length**, not `total.min(limit)`. Fix everywhere pagination exists; test offset near the end of the list.
